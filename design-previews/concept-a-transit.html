      One agent or many?

      Some tasks need a specialist, some need a team, and some need a whole department. Here is how to tell which one you are building.

      14 min rideUpdated 12 Oct 20262,418 riders
      Listen on board0:00 / 13:52

      When you picture an AI agent, you might imagine one clever system that handles everything. In practice the choice between a single agent and a team of agents is one of the biggest design decisions you will make.

      01Five kinds of agent

      Before combining agents, it helps to know what each kind can do on its own. Think of these as skill levels for AI employees.

      Reflex agents follow rules

      They react to what is in front of them using fixed rules. A smoke detector is a reflex agent: it senses smoke and rings. It doesn't know why, and it doesn't plan.

      Platform notice · real-world example

      A robot vacuum is a model-based agent. It maps your home, remembers which rooms are done, and skips them on the next pass.

      Goal-based agents plan

      They hold a target state and search for actions that reach it. A navigation app re-routing around traffic is the everyday version.

      02When one agent is enough

      A single agent is easier to build, test and observe. If the task fits in one context window and needs one set of tools, adding more agents mostly adds latency and failure points.

      Add agents when the work splits, not when the demo needs drama.

      03Teams of agents

      Multi-agent systems give each agent a narrow role: a planner, a researcher, a writer, a reviewer. A coordinator passes work between them and decides when the job is done.

      PatternBest forWatch out for
      Single agentFocused tasks, one toolsetContext overload on long jobs
      Supervisor + workersResearch, report writingSupervisor becomes a bottleneck
      Peer handoffSupport triage, routingLoops between agents

      04Choosing your architecture

      Start with one agent. Measure where it fails. Split out a second agent only for the part that fails for a reason a specialist would fix, such as a different toolset or a long-running subtask.
